# Seasonal Newsletter Drafting Template

## What’s Up, St. Paul’s?

*Connecting our church family*

## How to Use This Template

This document is the working draft for one seasonal newsletter. Make a fresh copy for Spring, Summer, Fall, or Winter.

You do not need to fill every section. Start with the Core Sections, then choose only the Optional Story Modules that fit this season’s ministry, message, and church life.

Keep the writing warm, clear, and easy to scan. Short paragraphs are best. If something does not apply, leave it blank or mark `REMOVE`.

## Seasonal Workflow

1. Fill in the Newsletter Basics.
2. Complete the Core Sections.
3. Choose the Optional Story Modules that fit this edition.
4. Add the most important upcoming events.
5. Add photos or note which photos will be provided.
6. Check names, dates, times, links, and permissions.
7. Submit the approved draft for newsletter design and HTML rendering.

## Ready for Newsletter Design

Once this draft is approved, submit it as the source for the final *What’s Up, St. Paul’s?* newsletter.

The final newsletter design can change from season to season. Sections may be reordered, combined, expanded, shortened, or removed to best tell the story of that edition while keeping the St. Paul’s visual identity consistent.

## Editorial Style

Write in a warm, hopeful, Christ-centered voice. Sound like a caring church family talking with one another.

Prefer:

- “we,” “our,” and “us”
- Short paragraphs
- Clear headings
- Specific stories and examples
- Exact names, dates, and details
- Warm invitations
- Scripture when it naturally supports the story

Avoid:

- Corporate language
- Unexplained church terminology
- Guilt-driven appeals
- Long blocks of text
- Too many exclamation marks
- Repeating the same message in several sections

## Master Reminder

Every newsletter can be different.

The goal is not to fill every box. The goal is to tell the most important stories of this season clearly, warmly, and faithfully—while keeping every issue unmistakably St. Paul’s.

# Email Production Addendum

This addendum governs HTML implementation after the seasonal Google Doc draft has been approved. It must not be used to restore optional modules the approved draft omitted or to rewrite approved copy.

## Editorial-to-HTML Structure

1. Use the selected seasonal hero.
2. Preserve the three Core Sections in their approved order unless the approved draft explicitly directs otherwise.
3. Render only the Optional Story Modules selected in the approved draft.
4. Preserve the approved order of selected modules; design may combine or reorder only when the approved draft or editor authorizes it.
5. Include 3–5 priority events, the gratitude section, and current footer information.
6. Remove all unused drafting prompts, brackets, checkboxes, and `REMOVE` markers before release.

## Desktop and Mobile Layout

- Main container: `width:100%`, `max-width:1100px`, centered.
- Use a full-width mobile fallback.
- At approximately 600px and below, stack multi-column sections into a logical single-column reading order.
- Use nested presentation tables; do not use CSS Grid or Flexbox for email layout.
- Keep table structure readable when media queries are ignored.

## Accessible Typography

- Headings: Lora, Georgia, serif.
- Body: Inter, Arial, Helvetica, sans-serif.
- Desktop main title: approximately 48–56px.
- Desktop major section headings: approximately 34–42px.
- Desktop body copy: 18–20px minimum with 1.65–1.8 line height.
- Mobile major headings: approximately 26–32px.
- Mobile body: approximately 17–18px.
- Keep paragraphs short; the approved Google Doc’s 120–200-word recommendation applies to Greetings Friends. Other module lengths are content-driven.

## Brand Colors

- Deep navy: `#0A1C2C`
- Slate navy: `#1E293B`
- Body slate: `#475569`
- Soft slate: `#64748B`
- Gold: `#D4AF37`
- Deep gold: `#B8860B`
- Light gold: `#F0D98C`
- Cream: `#FDFBF7`
- Soft blue: `#EBF4F8`
- White: `#FFFFFF`

On dark navy backgrounds, use white headings, `#E2E8F0` or `#CBD5E1` body text, and gold accents. Never use dark slate text on dark navy.

## Card and Visual Language

- Main newsletter and major cards: 24px radius.
- Inner cards: approximately 16–20px radius.
- Small event and gratitude cards: approximately 14–16px radius.
- Buttons: 40–50px pill radius.
- Use small uppercase labels, serif headings, gold dividers, cream editorial cards, navy feature panels, and selective gold/bold skim emphasis.
- Use bento-style pairings only where the approved modules benefit from them and the mobile reading order remains clear.

## Canonical v4 Icons

Use `resources/links/st-pauls-icons-v4.json` as the machine-readable source and `resources/links/st-pauls-icons-and-important-links.md` as the human-readable role map.

- Icon directory: `assets/icons/`
- Base URL: `https://custodybuddy.github.io/st-pauls-newsletter-assets/assets/icons/`
- Main branding icon: 88px.
- Major section icons: 72px.
- Use descriptive alt text for meaningful icons and `alt=""` only when decorative.
- Do not use retired icons or emoji substitutes.
- A selected story module may use the closest documented v4 role; use a text-only heading when no mapping is semantically appropriate.

## Images

- Use absolute HTTPS image URLs in final email HTML.
- Include explicit `width` and `alt` attributes.
- Use `display:block; border:0; outline:none; text-decoration:none;` on images.
- Hero master width: 1100px.
- Do not publish an identifiable-person image without appropriate permission.
- A link or image note in the approved draft is an input for production, not necessarily the final hosted URL.

## Email-Safe HTML

Use:

- Table-based layout
- Inline critical styles
- Explicit colors
- Absolute links and image URLs
- `border="0" cellpadding="0" cellspacing="0"` on tables
- `role="presentation"` on layout tables
- Simple mobile stacking classes as progressive enhancement

Avoid:

- CSS Grid or Flexbox
- JavaScript
- Forms
- Relative image or link URLs
- Embedded base64 images in send-ready HTML
- Unsupported or untested SVG icons
- Complex background images unless tested

## Links and Footer

- Use `resources/links/st-pauls-website-data-and-links-v1.md` for current destinations.
- Verify time-sensitive event and bulletin links before sending.
- Include a discreet View in browser link in the footer using the ESP’s exact merge tag.
- Never send `[VIEW_IN_BROWSER_URL]`, `href="#"`, or a generic hard-coded browser-version URL.
- Preserve the approved footer facts unless the current source explicitly updates them.

## Production Workflow

1. Confirm the linked Google Doc or an explicitly assigned copy is the latest approved editorial source.
2. Confirm the three Core Sections and identify the selected Optional Story Modules in their approved order.
3. Create a new versioned HTML file in `newsletters/working/`; never overwrite an approved or historical issue.
4. Convert approved content to email-safe table HTML without rewriting it.
5. Apply the current v4 icon map, brand system, responsive stacking, and accessibility rules.
6. Remove unused drafting scaffolding and verify all names, dates, times, links, financial figures, Scripture, images, and permissions.
7. Run `node scripts/audit-newsletter-repo.js` and resolve every current-source error.
8. Send real inbox tests to Gmail, Apple Mail, Outlook, Yahoo, and mobile clients when available.
9. Approve the final rendered issue before distribution.
